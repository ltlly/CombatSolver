## 调用链证据

从既有同版本IL引用/异步映射连接默认定义与Hook状态机，每条保留调用者MethodDef、操作数token、offset及源码位置。98个包含调用者的正文标记为88个直接完成、7个上下文包装、3个同时存在两者。定位脚本不解析C#语义或动态路径，计数不是所有输入的实际执行次数；每个有效派发的条件仍要核对。

`HookPlayerChoiceContext.AssignTaskAndWaitForPauseOrCompletion`在Source非空时先执行包装器，包装器await原任务再分派完成事件，随后才把包装任务写到上下文并完成自己的TCS。原生已完成任务观察中，事件发生时上下文Task仍为null；完成后栈保留单个Source、Owner保持、未创建GameAction。Owner-only上下文不取得Source或模型栈。故原正文里没有直接Invoke也不能认定没有完成事件。

四个Hook具有实际Ritsu生命周期发布补丁；它们会发布回合开始/结束、死亡事件，两个后置入口还包装返回Task。首个“零补丁”原生合同因此明确拒绝。随后只为观察逐项锁定实际补丁种类、方法、MVID、IL与补丁方法自身0补丁；**没有将其事件受众认证为空或纯，也没有放宽生产证书。** 原生构造器还有一项能力Owner修正Postfix；其条件为Source实现IModelCapability，本次真实DefendSilent不满足此条件。未知补丁继续拒绝。

## 更合理的证明组合

证明应以完整结算为单位：方法体与实际虚派发、调用方消费/上下文、有效补丁与通知受众、初始及未来来源闭包、分支状态与政策见证分别成立，才能组成剪枝资格。不要将179个默认方法体的局部证据提升为整根认证。

回复上界、药水库存封闭、消耗堆顺序可观察性和搜索阶段资格必须独立认证。零回复不能证明不会补药或读取消耗顺序；证明能用于剪枝也不能自动开放前置计划。未知部分继续原搜索。

胜利界继续使用完整合规获胜路线，对所有合法未来组合证明其最乐观质量仍严格更差；同HP时还有药水、成长、保命、遗物和追回目标，未独立证明这些比较轴时保留。联合回复/成本关系复用[既有研究](joint-recovery-cost-research-20261007.md)，其两个库存认证根仍没有回复库存，不重复做零机会请求。保序投影复用[既有观察](exhaust-projection-subsets-20261007.md)的猎手/亡灵76679/21198次潜在准入；它们不是实际剪枝，不能作为提速。

下一步只针对该投影的实际根，连接已定位来源、监听getter、事件/清理与生成/回收闭包，形成组件认证；不同目标分别拒绝未知来源。已有默认方法与本轮调用链证据按原范围复用，不再扫描相同DLL或重复相同直接调用。原完整键继续服务排序、续用与诊断，生产判重接入后再做完整状态/Fork/RNG和整请求交错验收。
