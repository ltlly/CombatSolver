## 联合回复界

令 `R` 为已记录回复，`T` 为所有合法未来回复总量的安全上限，`C=maxHp-hp` 为当前缺血，`G` 为未来生命容量增加总量的安全上限。候选乐观回复为：

```text
R + min(T, C + G)
```

若未来实际受伤为 `D`、实际回复为 `H`，必须独立证明 `H<=T` 与 `H<=D+C+G`。在这些前提下，对现有正整数回复价值除数 `k`：

```text
D - floor((R+H)/k) >= -floor((R+min(T,C+G))/k)
```

Z3 5.1.0 对 `k=1、5、536870911` 的整数公式均返回 `unsat`，即前提内没有低估战损下界的反例；没有枚举上限。另验证生命封顶只能减少实际增量。证明仅覆盖这个标量不等式，不证明来源闭包、死亡重设、最大生命成本、成长奖励、条件遗物、用药资格或有限Beam质量。

现有 `OptimisticRecoveredHp` 仅使用 `C`。满血情况下，直接给果汁添加有限回复5会把乐观回复裁成0，而实际 `GainMaxHp` 同时增加当前生命；Z3给出 `R=D=C=0，T=G=H=5` 反例。**这不是现有合法果汁已经错误剪枝的证据**：当前合法持有果汁仍得到无限界，已知来源估计和组件证明均拒绝它。联合界旨在为将来的有限来源扩展保留必要容量，`G=0` 时与原公式相同，并非让所有现有认证都变得更紧。

一次性值类型原型使用 `long` 做加法，未知哨兵、负数、非法HP及结果溢出返回拒绝。它不捕获live、不登记来源，也没有进入搜索或正式源码。

## 实际通知链与未审计范围

盘点得到直接受众三个精确方法：原生顶部HP更新、原生Tracker转发、本项目独立战绩观察。Tracker嵌套受众有七种方法、八个实例：Ritsu调试面板及原生回合按钮、手牌、生命展示、球管理、能量、意图展示；这些入口在本次盘点没有Harmony补丁。没有据此认定它们全部安全。

读取当前实际DLL的方法体还发现：

- Tracker重算会调用每张牌的附魔 `RecalculateValues`，随后再分派嵌套受众。
- 手牌通知在选择模式会执行 `_currentSelectionFilter`，还能完成选择的Task；“界面回调”不是充分的无副作用证明。
- Ritsu调试面板的延迟刷新可进入页面注册表、次级资源定义和详情刷新；页面变更还有下一层事件。实际本轮没有证明这些注册表、子节点及动态委托的闭包。
- 复用对应MVID的旧完整IL引用清单，提取24个相关事件访问/订阅位置；原版CubexConstruct还订阅当前生命变化。定向读取其回调仅设置音效参数，不把所有原版模型当作默认安全。

这份清单只覆盖原生直接静态引用及本次已建局受众。反射订阅、依赖程序集的其他注册、未来召唤、界面开关/选牌变化、方法以下的补丁与动态回调、死亡/复活及生命直接重设仍需审计。当前组件覆盖率不能因此增加；也不能把先前10/11根的类型准入写成已完成所有事件来源证明。

下一实现应在主线程稳定根及live采用边界核对直接事件和通知转发的完整受众，采用精确方法、实际实例、版本及补丁组合证明；未知来源明确拒绝。只缓存不可变元数据，不把可变受众缓存到worker，也不让后台调用live回调。新增生成/召唤后的受众与再生、药水额度、条件战后回复、生命上限和复活预算必须分别证明，不能用扩大类型表替代。

只有来源证明完成，才把 `T/G` 纳入现有 `StrategicHpRecoveryBound` 和完整胜利见证入口；保留胜负、战损、药水、成长、遗物目标、追回和保命资源比较。严格更差才剪，相等战损继续保留。联合标量界不能单独替代这些政策门禁。
