# 剩余重场景的共性成本（2026-10-05）

剩余慢根应按共同机制优化：完整请求中的多个互补搜索、每次候选的状态评估与分支复制，以及高密度选牌展开。回复上界继续复用现有组件证明和上游共享表；它不能覆盖尚未找到完整胜利的根，也不能代替状态处理的通用降本。

共性分析阶段复用已有结果与 trace；随后仅做保持原完整评估行为的中间状态类型原型、最小合同和两根诊断。原型已撤回，最终源码不含运行时改动，也没有新增性能验收。基于已交付分支 `88e90001` 建立 `perf/common-state-cost-20261005`，不重新开始已有实验。女王两根仍按用户要求暂停。

## 证据口径

[结构化结果](heavy-scene-common-costs-20261005.json)保存输入文件 SHA256、逐阶段成本、工作量、质量和原始路径。前五项来自合并 PR #211 后的阶段 DLL `79baf3a3…`，不是随后开局药水准入合入后的最终 DLL `e04003a5…` 新验收。后两项为更早版本，单独标明，不能与前五项合并成当前覆盖率。

固定根使用已有 VeryHigh、DOP16、原牌序/RNG/政策和预算；上传包保留其原生 VeryHigh 配置。原固定语料与上传包的实际宽度、节点预算及运行宿主不同，不比较它们的转换吞吐。下表时间为完整 Coordinator 的 `totalElapsedMilliseconds`，每项均核对阶段时长之和；离线进程/宿主 wall time 另存，不能与原生 Coordinator 时长混称。

主要额外成本因机制不同而变化：储君开局能力成员6.702秒、精炼5.405秒；猎手首领精炼9.687秒、Smart梯度4.869秒；亡灵首领精炼10.446秒、Smart梯度6.150秒；大牌组开局能力44.016秒、精炼42.408秒；上传灵魂枢纽精炼77.529秒、开局用药后续33.243秒。

这些阶段有真实质量作用：已有灵魂枢纽记录中，无药路线由主宽度28战损改善到窄成员19、宽成员16，再由合法力量药水路线改善到6；储君主宽度48、精炼46、开局能力路线40。更早千足虫记录也是主宽度36、开局能力路线20。不能通过取消这些成员、缩预算或取消药水审计获得提速。通用降本必须进入所有成员共用的候选执行与评估路径。

## 2. 选牌与牌组规模是两种放大器

更早亡灵千足虫记录为479.198秒、11,313,259次转换、4,544,883个选择分支；更早亡灵永世沙漏为56.260秒、1,516,371次转换、1,136,792个选择分支，选择密度74.97%。后者两次 PrimaryBeam 最终仍是 NoWin。它们说明高密度选择不能用“药水很多”或“只要认证回血”统一解释；这些旧时间不是当前版本重新测量。

五个近期样本每次转换的 worker 累计分配分别为39.17、41.23、36.24、95.39、41.53 KB。396张牌的合成根显著放大牌堆扫描和复制。累计分配不是存活内存，更不是进程峰值；不能用其下降推断通过峰值门槛。

现有手动卡牌和药水执行前缀已经覆盖41张原版卡、9种原版药水。下一步应按实际退回完整回放的共同来源扩展现有入口，而不是重复实现这一批支持。已记录的前缀命中、捕获和 incumbent 剪枝多数属于选中 solver，不能把它们与整个请求的转换数直接组成总命中率。

## 3. CPU 与分配给出的具体方向

复用[储君成本研究](regent-search-cost-research-20261005.md)的同一份199Hz CPU trace及校正窗口，最近自有职责的排他归因为 Replay40.206%、Snapshot27.696%、Fork10.105%、Retention2.060%。这是一个根、一个历史候选的采样，不能称所有场景都有同样占比，也不能把它们相加作为可取得的提速。

源码中每个 Snapshot 会构建完整状态键、投影洗牌顺序、威胁和多项牌库/手牌特征。Fork 则复制分支卡牌 wrapper、Power 及引用映射。选择会同时增加这些共同步骤的调用次数，长战斗和多个搜索成员再放大请求总量。

本轮进一步分析同一份完整87902组分配栈，没有再次采搜索：

| 含PowerModel.DeepCloneFields的互斥调用链 | 采样估算字节 | 占12.720 GB搜索分配 |
| --- | ---: | ---: |
| DynamicVarSet构造链 | 389,520,752 | 3.062% |
| DynamicVarSet.Clone，构造链之外 | 242,403,016 | 1.906% |
| 其他Power深复制 | 20,150,544 | 0.158% |

此前最近自有调用 `CloneModelForSimulation` 的约1.463 GB含有更广调用，不能全部当作Power变量集合构造的可移除成本；构造链自身也含必须保留的变量副本。没有把阶段总量误当一个小 helper 的收益空间，因此本轮不实现扩大原生克隆语义面的集合微优化。

同时核对同一安装DLL的实际原生调用链：Power深复制先调用基类，再执行 `DynamicVars.Clone(this)` 和 `InitInternalData`；变量集合执行逐变量Clone和owner初始化；单个变量Clone会重设基础预览，框架另有稀疏元数据复制补丁。任何后续复制优化都必须保留这些行为、事件清理及Fork独占性，不能直接共享可变变量或省略回调。

## 4. 通用优化的验证顺序

优先调查“需要完整保路评分的候选”与“只用于继续选牌的中间状态”能否延后部分派生评估。先逐一核对消费者、状态键和转置标签：Score等字段参与原支配关系，不能仅因为后续会去重，就把完整Snapshot跳掉或填默认值。后续测量见下一节：机会较小，已撤回原型；没有延后评估的安全性证明或实测提速。

其次调查按严格依赖缓存牌堆派生特征。利用已有卡牌/牌堆失效与Fork边界；费用、动态变量、附着模型、全局关键字或生成来源会改变依赖时，必须失效或旁路。投影洗牌仍须保留原排序、等价牌的原生次序及RNG，浮点累加也不能随意重排。它是针对牌组规模的通用能力，不按遭遇名准入。

再按日志中的实际回退来源扩大现有选择续接，复用唯一结算尾部和分支重映射。认证与共享胜利界继续作为另一条通用路线：仅在同政策完整获胜见证和资源桶证明存在时使用，对未知来源和未找到胜利的根保留搜索。

固定小工作量先选储君首领、亡灵首领和396张牌根，分别暴露多成员、选择密度和牌堆规模成本。改变状态派生/复制时先做最小原生、完整状态、Fork、RNG和live隔离验证；性能测量单独进行。只有证明有收益的候选才跑最终串行交错整请求及回归。普通测试保持120秒上限，灵魂枢纽900秒启动器授权仍只适用于该包和其对照。

## 5. 待选牌评估机会：原型撤回

[实验索引](pending-choice-evaluation-opportunity-20261005.json)保留源码基点、23份文件的本地补丁、诊断DLL、输入及结果哈希。先引入只能携带续接所需状态的类型，保留原完整Snapshot；选牌展开的稳定输出和SearchNode仍要求完整评估类型。StandPat、完整回放、准备阶段和需要读取评分的探针继续走原评估。延后评估开关始终为false，没有填零分数、改选择顺序、预算或政策。

该类型边界的Release构建零警告/错误；独立原生 `CARD-CONTINUATION-SEARCH` 合同通过，runId为 `4ec5d4c324b84beca0b1e659c908b6cf`，27.885秒，实例已清理。初次编译有类型消费者错误；独立构建目录首轮启动因缺manifest被启动器拒绝，未启动测试；修正各自失败原因后通过。这只证明保持完整评估的类型边界，不能称延后评估通过严格差分。

随后只测原完整Snapshot在可延后路径上的成本。两根均为DOP16、原VeryHigh宽度135/选择上限72、42、54，使用显式小节点和60秒诊断预算，单成员Evaluate、普通GC、阶段插桩；它们不是原完整Coordinator验收：

累计时长来自合并worker的Stopwatch，包含等待和GC，不能当作CPU占比或预计整请求提速。已有选择续接使大部分选择分支直接得到稳定结果；高选择密度并不表示同样比例的可省中间快照。两根诊断耗时分别16.069、6.457秒，原型没有启用延后计算，因此没有候选对照速度或内存门槛结论。
