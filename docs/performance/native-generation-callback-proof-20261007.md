## 原生反例与版本

实际安装的游戏为 `0.111.0 / 41cef1ea`，`sts2.dll` SHA-256 为 `2b40d2df538db1ceb5fa48d958c80ab730ada1e07db88a870aff01a661768b9f`，MVID 为 `8a76776c-0ce1-4d4f-90bd-8cce653dad8e`。实际加载的 RitsuLib 0.6.6 兼容运行库 SHA-256 为 `fe387f765a3951690b161c129731e6c10016215c06074aa3356dd96290f13b52`，MVID 为 `f7f18a36-8ebb-4db2-b1ea-7bd340579646`。证据依据这两份 DLL 的当前调用链，不推及其他版本。

`CreatureCmd.Heal` 当前有一个 Ritsu 前缀，依次执行加法、倍率和末段治疗回调。其监听来源包括原生模型、附着能力和独立全局注册表；后者不属于原生 `ModHelper` 两类订阅者。注册表以 `Volatile.Read` 发布不可变快照，检查可以不执行未知监听器。

原生实验 `9020054e6408485095b37362a9675ca4`（25.741 秒）复现：储君，永久身份防御牌，HP 35，已生效再生 5，无其他药水、Power 或遗物。无扩展时回复上界为 `5+4+3+2+1=15`。注册一个治疗倍率为 2 的独立全局监听器后，旧根依然取得组件证书，上界仍为 15，两类 Mod 订阅者数量均为 0；调用五次实际 `RegenPower.BeforeSideTurnEndEarly` 后，原生 HP 35→65，实际回复 30。

这是五次独立原生回调的上界低估，未执行完整原生战斗，也未证明实际错误剪枝或错误终局。它与已暂停的丢路调查分开。未来生成牌的未知 `OnPlay` 接纳反例复用[上一轮证据](initial-generation-finite-recovery-pruning-20261007.md)，没有重复运行。

## 保留的修复及范围

- 稳定根捕获和 `ContinuationStamp.CaptureLive` 检查当前 `Heal` 补丁组合。无补丁时原生命令不派发该流；有补丁时仅接纳上述运行库中已审计的单个精确前缀。未知组合、版本或非空全局治疗监听表明确失败。
- 在现有初始牌、完整当前牌集合及永久牌组检查之外，审计五角色及无色规范池中通过原生战斗生成标记、非 Ancient/Event 的保守超集，同时检查固定状态牌与诅咒牌池。玩家人数和解锁限制只收窄随机池；该超集不是实际随机生成算法，不抽 RNG。Feed、NotYet、Alchemize 不获得普通随机生成资格，初始持有仍独立检查。
- 路线采用前重新检查补丁与全局监听表，防止根捕获后的注册变化被沿用。缓存只含反射元数据，后台与 Fork 不读取注册表或其他可变 live 数据，不执行未知回调。

这里修复了两种具体来源缺口，**没有完成回复来源封闭证明**。其他 Ritsu 生命周期全局监听、模型治疗接口、附着能力、能力默认构造修正、固定特殊生成/复制/回收及其他命令补丁仍需逐项审计。既有 `affectsGameplay=false` 信任规则保持，并未证明任意第三方方法安全。对未知来源采用明确拒绝，不增加第三方战斗内容适配。

原生探针记录 718 个被补丁修改的游戏目标，其中未来牌 OnPlay 状态机的 11 项现有修改来自 Ritsu 手牌上限与本项目即时执行。该表用于定位调用链，数量与程序集身份不构成安全证明。全部元数据、反编译输出及实验源代码见[结构化记录](native-generation-callback-proof-20261007.json)。
