## 保守原型与撤回原因

原型只认证六个玩家库存事件和每瓶初始药水 `BeforeUse` 事件的受众全部为空。只在主线程捕获，缓存字段元数据，不缓存可变委托或读取worker之外的live值；未知布局与非空受众返回无库存证明。

首次原生验证在正常根即失败。新只读受众盘点确认 `MaxPotionCountChanged` 有 `NPotionContainer.GrowPotionHolders` 和 `NTopBar.MaxPotionsChanged` 两个原生接收者；获得、丢弃、已用移除、获取失败事件也各有原生药水栏接收者。

事件存在本身不证明会补药；属于原版程序集或名为界面方法也不证明无副作用。因此，这个全空原型没有直接投入生产，也没有改成默认放行原生接收者。六事件/两瓶BeforeUse拒绝矩阵、正向库存剪枝、两次原生完整状态和16Fork的后续断言未执行，不能列为通过。

## 接下来可实施的剪枝合同

复用[联合界数学证据](joint-recovery-cost-research-20261007.md)，对同一合法剩余用药组合一起计算回复上限和成本下限，再按现有Smart节血要求比较完整无药胜利；不能拼接一组的最多回血和另一组的最低成本。只有每个可能组合都不符合政策时，才否证该精确剂量层；相等继续搜索，已有再生、战后门槛回复、成长及保命资源保持原评价。

库存闭包必须独立证明：初始/永久牌组、全牌堆及待返回牌、生成/变牌/复制/重放/回收、遗物取得、敌人/召唤、槽位别名、公开事件和原生Hook都不能引入漏算的合法药水。当前受众、后续受众及live采用边界分别核对，未知保留原搜索。正常界面受众需要准确方法、实际实例、下层信号/委托及补丁组合的证明，不能用程序集、文案或黑名单替代。

既有两个类型表准入根没有药水回复，因此同组合联合界在它们上退化为原最低成本界；仅增加联合计算不会产生新剪枝。应先选择具有回复库存且库存证明成立的根观察实际否证数量，再决定实现和性能验收，避免为没有机会的根添加认证成本。
